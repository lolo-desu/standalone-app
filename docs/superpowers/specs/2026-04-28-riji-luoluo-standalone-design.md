# 日记络络独立桌面版设计稿

## 目标

把当前依赖 `SillyTavern + JS-Slash-Runner + lolocard` 运行的 `日记络络`，改造成一个可独立运行的桌面应用。

第一阶段产品目标是：

- 只服务 `日记络络` 这一部作品
- 应用启动后进入独立游戏主菜单，而不是酒馆聊天页面
- 游戏内始终停留在 galgame 风格宿主界面
- 具备传统 VN 风格的存档、读档、log 回溯和快速存读档
- 支持双模型路由：故事模型负责最终文本，逻辑模型负责变量和状态控制

架构目标是：

- 第一阶段围绕单作品落地
- 结构上保留后续扩展到多作品宿主的空间
- 尽可能复用现有 JS/TS 资产
- 不继续沿用 SillyTavern 的楼层聊天宿主作为最终产品形态

## 方案结论

采用以下总体方案：

- `Electrobun` 作为桌面宿主壳
- 新建独立游戏前端宿主
- 新建 `Host Adapter` 作为运行时桥接层
- `Node` 子进程承载 `SillyTavern` 可复用能力层
- `lolocard` 的 `日记络络` 作为首个内容包
- `JS-Slash-Runner` 复用可移植的 runtime、工具函数和部分前端表现能力

不采用以下路线：

- 不把 `SillyTavern` 原前端壳继续当作最终宿主
- 第一阶段不强行把 `SillyTavern` 后端迁移到 Bun
- 第一阶段不做完全重写的一套全新变量/世界书/runtime 系统

## 非目标

第一阶段明确不做：

- 通用多作品平台完整产品化
- 章节树回退、分支树回看、任意时间轴跳转
- 用存档直接保存明文 API Key
- 完全摆脱所有 `SillyTavern` 能力依赖
- 一次性重写所有 `lolocard` 和 `JS-Slash-Runner` 运行时

## 系统分层

### 1. Desktop Shell

技术选型：`Electrobun`

职责：

- 创建和管理桌面窗口
- 管理应用启动与退出
- 提供本地配置目录和存档目录
- 管理资源根路径
- 提供桌面壳与前端之间的基础桥接

这一层不直接承载故事规则和变量逻辑。

### 2. Game Frontend Shell

这是最终用户看见的应用前端，不再复用 `SillyTavern` 的聊天宿主 UI。

职责：

- 主菜单：`继续 / 新游戏 / 加载存档 / 设置 / 退出`
- 新游戏初始化向导
- 常驻 galgame 风格主界面
- 底部系统操作：`Q.save / Q.load / save / load / log / setting / hide`
- `互动 / 移动 / 调查` 三类动作界面
- log 界面
- 存档/读档界面
- 设置界面

关键原则：

- 游戏内主界面始终是 galgame 宿主
- 不再是“某条 AI 回复被渲染成 galgame 样式”

### 3. Host Adapter

这是系统核心桥接层。

职责：

- 把前端 UI 动作转换成统一的游戏动作
- 统一管理 session、timeline、log、scene、save/load 和调查上下文
- 暴露变量、世界书、消息、事件、资源等统一接口
- 调用逻辑模型和故事模型
- 与 `SillyTavern` 能力层和 `lolocard` 内容层交互

这一层是替代原来 Tavern Helper 宿主语义的关键位置。

### 4. Engine Process

技术路线：第一阶段保留 `Node` 子进程。

职责：

- 复用 `SillyTavern` 的模型 provider 接入
- 复用提示词转换和部分内容处理链路
- 复用角色卡和世界书相关处理能力
- 提供本地接口给 `Host Adapter`

关键原则：

- 只复用能力层
- 不复用 `SillyTavern` 原宿主 UI

### 5. Content Runtime

职责：

- 承载 `lolocard` 的 `日记络络` 内容
- 复用其世界书、第一条消息、变量 schema、galgame 素材和规则
- 复用 `JS-Slash-Runner` 中可移植的 runtime、工具函数和部分前端表现能力

关键原则：

- `日记络络` 是第一阶段的首个内容包
- 内容迁移时尽量不改写故事与素材本体
- 运行时从“消息楼层内插入 UI”转向“由独立宿主直接承载 UI”

## 产品主流程

### 启动流程

应用启动后，进入主菜单。

主菜单按钮：

- `继续`
- `新游戏`
- `加载存档`
- `设置`
- `退出`

### 新游戏流程

新游戏使用初始化向导。

初始化内容：

- 模型渠道 / provider
- Base URL
- API Key profile
- 单模型或双模型
- 故事模型
- 逻辑模型
- 必要的默认生成参数或风格预设

完成后：

- 创建新的 `session`
- 初始化变量状态
- 初始化第一条消息与场景状态
- 进入常驻 galgame 主界面

### 游戏内流程

游戏内始终停留在 galgame 主界面。

底部系统操作：

- `Q.save`
- `Q.load`
- `save`
- `load`
- `log`
- `setting`
- `hide`

主动作：

- `互动`
- `移动`
- `调查`

推进方式：

- 点击继续
- 空格继续播放
- 播放结束后弹出选项

## Session 结构

一个 `session` 代表一次完整游玩。

至少包含以下数据：

- `session_meta`
  - session id
  - 作品 id
  - 创建时间
  - 最近使用时间
- `model_config`
  - provider id
  - credential profile id
  - story model
  - logic model
  - 是否双模型
  - 当前关键生成参数快照
- `game_state`
  - 玩家位置
  - 络络位置
  - 当前地点
  - 当前场景模式
  - 当前可用动作
- `variable_state`
  - `stat_data`
  - 与世界、主线事件、角色状态相关的变量集合
- `timeline_state`
  - 完整运行时间线
- `log_state`
  - 给玩家回看的正式记录
- `scene_state`
  - 当前界面呈现状态
- `investigation_state`
  - 临时调查上下文与剩余轮数
- `save_meta`
  - 最近自动存档信息
  - 快速存档信息
  - 手动存档索引

## 三套核心数据模型

### Timeline

`timeline` 是真实运行时间线。

职责：

- 记录游戏推进过程中的真实状态变更
- 保存动作、输入、变量 patch、场景 patch、逻辑结果和故事结果
- 作为系统内部运行依据

每个 `timeline node` 可以包含：

- 动作类型
- 原始输入
- 逻辑结果摘要
- 故事结果摘要
- 变量变更
- 地点变更
- 场景变更
- 可选项更新
- 是否进入 log
- 是否触发自动存档

### Log

`log` 是玩家回看记录，不等于 timeline。

职责：

- 提供传统 VN 风格回看体验
- 只保存适合阅读的正式内容

记录：

- 正式互动输入与结果
- 正式移动后的叙事
- 正式系统提示
- 关键剧情变化摘要

不记录：

- 调查弹窗正文
- 纯 UI 操作
- 中间逻辑判定细节

### Scene

`scene` 是当前画面状态，不是历史。

职责：

- 驱动 galgame 常驻主界面
- 决定当前前端应显示什么

至少包含：

- 当前背景
- 当前立绘
- 当前角色表情/姿势
- 当前显示文本
- 当前名字框
- 当前选项
- 当前界面模式

界面模式至少包括：

- 普通对话
- 选项中
- 地图
- 调查弹窗
- log
- setting
- hide

## 三种核心动作

### 互动

这是正式推进动作。

用户体验：

- 打开输入框编辑器
- 可点击快捷按钮如 `【】`
- 提交文本后推进剧情

运行方式：

- 形成 `InteractAction`
- 进入正式上下文
- 会调用逻辑模型与故事模型
- 结果写入 timeline、log、variable_state、scene_state
- 会触发自动存档

### 移动

这是正式推进动作，但输入方式是地图选择。

用户体验：

- 打开地图
- 显示玩家位置、络络位置、可前往地点
- 选择地点后推进剧情

运行方式：

- 形成 `MoveAction`
- 先进行地点合法性判断
- 调用逻辑模型判断状态与事件
- 调用故事模型输出到达后的叙事和表现
- 结果写入 timeline、log、map/game state、scene_state
- 会触发自动存档

### 调查

这是临时动作，不属于正式推进回合。

用户体验：

- 打开调查弹窗
- 展开周围环境描述

运行方式：

- 形成 `InvestigateAction`
- 读取当前地点和场景状态
- 产生环境描述与临时上下文
- 不写入正式 log
- 不触发自动存档
- 只写入 `investigation_state`

保留规则：

- 调查结果只在接下来三轮正式推进中参与上下文
- 每经过一轮正式动作，剩余轮数减 1
- 归零后丢弃

## 双模型路由

### 故事模型

职责：

- 生成最终叙事文本
- 负责角色说话与文风表现
- 生成场景表现相关内容
- 输出适配 galgame 展示的可见文本

### 逻辑模型

职责：

- 控制变量更新
- 判定地点、事件、条件和状态转移
- 生成给故事模型的结构化约束
- 控制地图、界面模式和规则行为

### Adapter 聚合输出

前端只消费 adapter 结构化结果，不直接消费任意模型的原始输出。

统一输出至少包括：

- `state_patch`
- `scene_patch`
- `display_payload`
- `choices`
- `log_entry`
- `autosave_required`

## 模型配置与 API Key

### App Level 配置

应用级配置保存：

- provider 列表
- Base URL
- API Key profile
- 默认故事模型
- 默认逻辑模型
- 是否启用双模型
- 默认生成参数

作用：

- 作为新游戏初始化的数据来源
- 供多个 session 复用

### Session Level 配置

session 保存：

- provider id
- credential profile id
- story model
- logic model
- 是否双模型
- 关键生成参数快照

作用：

- 保证读档时配置一致
- 避免全局默认值变化影响旧存档

### API Key 保存策略

第一阶段规则：

- API Key 不进入存档文件
- 应用配置保存真正凭据
- session 只保存 profile 引用

这样保证：

- 存档文件不散落明文 key
- 实现仍保持较小复杂度

### 读档时的模型配置规则

- 读档后优先恢复存档绑定的 provider/profile/model 配置
- 如果凭据失效或不存在：
  - 阻止继续推进剧情
  - 提示重新绑定凭据
  - 允许先进入存档查看界面

## 存档系统

采用传统 VN 风格整局快照存档。

### 存档种类

- `save / load`：普通手动存档槽
- `Q.save / Q.load`：快速存档槽
- 自动存档：正式推进后更新 1 个自动槽

### 存档语义

读档时直接恢复到当时的完整状态，而不是跳到某个章节重新跑一遍。

### 每个存档保存的内容

- 当前剧情节点
- 当前 galgame 场景状态
- 当前变量状态
- 玩家位置
- 络络位置
- 主线事件状态
- 当前 log
- 当前调查短期上下文
- 当前可选动作状态
- 当前模型配置

### 第一阶段不做

- 章节树回退
- 分支树回看点
- 任意时间轴跳转

## 与现有仓库的职责边界

### SillyTavern

保留：

- provider 接入
- prompt 转换
- 角色卡处理
- 世界书和部分内容处理能力

不保留：

- 原宿主前端 UI 作为最终产品界面

### JS-Slash-Runner

保留：

- 可移植 runtime
- 工具函数
- 可能的 iframe / render 机制

不保留：

- 扩展面板式宿主存在形式

### lolocard

保留：

- `日记络络` 内容
- 世界书
- 第一条消息
- 变量 schema
- galgame 风格素材和规则

转变：

- 从“运行在酒馆消息楼层中”改成“运行在独立 VN 宿主中”

## 实现优先级建议

第一阶段优先完成：

- Electrobun 桌面壳
- 新前端宿主框架
- Host Adapter 最小闭环
- 传统 VN 存档与读档
- log 系统
- `互动 / 移动 / 调查` 三种动作最小闭环
- 双模型路由最小闭环
- `日记络络` 第一条消息到正式进入主流程

第一阶段可以暂缓：

- 通用多作品 UI
- 复杂回放系统
- 章节/节点回退
- 完整平台化管理能力

## 风险与约束

主要风险：

- 需要把 `lolocard` 和 `JS-Slash-Runner` 从楼层式消息宿主迁移到常驻 galgame 宿主
- 需要自己定义 timeline / log / scene 的新边界
- `SillyTavern` 作为能力层复用时，前后端边界要清晰，避免重新卷回原宿主结构

主要约束：

- 第一阶段优先保证小开发量与结构清晰
- 不为了追求纯粹架构而重做现有成熟能力

## 最终原则

这套设计的核心原则是：

- 复用 `SillyTavern` 的能力层
- 复用 `JS-Slash-Runner` 与 `lolocard` 的可移植内容和运行时
- 重建独立 VN 宿主层

也就是：

**不是把 galgame 塞进酒馆聊天系统，而是把酒馆的生成能力和内容能力接到一个新的 VN 宿主上。**
