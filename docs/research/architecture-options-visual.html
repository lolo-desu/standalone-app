独立宿主架构对比

目标：先做“日记络络”单作品独立桌面版，但内部架构保留未来多作品扩展空间。

方案 A

短期省事，长期难维护
ST 原前端壳
↓
往里硬塞 启动/存档/log/地图
↓
JS-Slash-Runner + lolocard
优点
  • 现成东西最多
  • 最早能看到效果
问题
  • 你想删掉的楼层系统恰好是它的核心
  • 最终会变成“魔改 ST”，不是独立游戏宿主
  • 新流程和旧 DOM 会长期互相拉扯

方案 B

推荐
Electrobun 桌面壳
↓
新游戏前端壳：启动/存档/log/地图/galgame UI
↓
Host Adapter：变量/世界书/消息/事件/slash/资源
↓
Node 引擎进程：复用 ST 能力层
↓
lolocard + JS-Slash-Runner 可复用部分
优点
  • 最贴合“独立应用”目标
  • 大量复用现有 JS/TS 资产
  • 可以逐步摆脱楼层系统
代价
  • 要自己定义宿主流程和 adapter
  • 前期要做一次消息模型重构

方案 C

最干净，但开发量最大
Electrobun / Tauri / Wails 壳
↓
全新前端宿主
↓
全新变量/世界书/消息/runtime
↓
只借用 lolocard 素材与 prompt
优点
  • 最终形态最纯净
  • 没有历史包袱
问题
  • 要重做太多已有能力
  • 最容易把项目拖大
推荐方向：方案 B
核心原则：复用“能力层”，重建“宿主层”。
产品结果：启动后直接进入 galgame 样式宿主，而不是先进入酒馆楼层聊天页。
