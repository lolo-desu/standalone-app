# 日记络络独立桌面版后续开发路线

## 背景

当前仓库已经具备 MVP 的基础骨架：

- `packages/shared` 已有 session/runtime 的共享契约
- `apps/engine` 已有新建 session、执行 action、save/load 的基础能力
- `apps/desktop` 已有 Electrobun 桌面壳、配置持久化、RPC 注入和 renderer 启动链路
- 游戏内 galgame 场景壳的视觉基线已经定稿

但距离“可完成开发并可持续迭代的 MVP”还差几个关键阶段。

当前最重要的现实约束有两个：

1. Windows 真机运行时仍存在 renderer 白屏问题，这是当前第一阻塞项
2. 主菜单、新游戏、save/load、log、以及游戏内动作闭环仍然没有全部打通

所以后续开发不能平均铺开，而应该按依赖顺序推进：

- 先修真实桌面运行时启动
- 再补齐玩家可见的主流程和动作闭环
- 然后加固存档和配置持久化
- 最后再推进 `日记络络` 内容接入深化与收尾 QA

---

## 第一阶段：先解决桌面端白屏

### 目标

让 renderer 在真实 Windows Electrobun 运行时里稳定挂载，不再出现纯白窗口。

### 为什么先做

因为 `README.md` 和 `docs/2026-04-30-local-dev-handoff.md` 都已经明确说明：
当前 repo 最大 blocker 不是功能缺失，而是桌面壳虽然能启动，renderer 仍可能在真实环境中失败。

如果这一层不稳定，后面的 UI 和功能开发价值都会下降。

### 重点文件

- `apps/desktop/src/renderer/index.ts`
- `apps/desktop/src/renderer/electrobun-entry.ts`
- `apps/desktop/src/renderer/main.ts`
- `apps/desktop/src/renderer/App.vue`
- `apps/desktop/src/electrobun-main.ts`
- `apps/desktop/src/bootstrap.ts`
- `apps/desktop/electrobun.config.ts`

### 可复用基础

- `apps/desktop/src/electrobun-rpc.ts` 里已有 renderer runtime 注入边界
- `apps/desktop/src/renderer/electrobun-entry.ts` 已有 bootstrap 边界
- 已有相关测试：
  - `apps/desktop/src/renderer/electrobun-entry.test.ts`
  - `apps/desktop/src/renderer/index.test.ts`
  - `apps/desktop/src/renderer/main.test.ts`

### 具体要做的事情

1. 给 renderer 启动边界补充定位信息，确认真实失败点
2. 找出失败发生在：
   - runtime 注入前
   - runtime 注入中
   - Vue app 创建时
   - 首次 render 时
3. 修掉真实 root cause，而不是猜测性改动 UI
4. 补 focused regression test，避免白屏问题回归
5. 本地用桌面壳重新验证真实启动

### 完成标准

- Electrobun 桌面窗口可以稳定显示 app shell
- 相关启动回归有测试覆盖

## 第二阶段：补齐应用主流程

### 目标

让应用从启动到进入游戏形成完整的单作品桌面产品路径。

### 重点文件

- `apps/desktop/src/renderer/App.vue`
- `apps/desktop/src/renderer/views/MainMenuView.vue`
- `apps/desktop/src/renderer/views/NewGameView.vue`
- `apps/desktop/src/renderer/stores/session.ts`
- `apps/desktop/src/renderer/stores/config.ts`
- `apps/desktop/src/renderer/api/client.ts`

### 可复用基础

- engine 侧已有 session endpoint：
  - `apps/engine/src/server.ts`
  - `apps/engine/src/routes/session.ts`
- config 侧已有本地存储与 RPC：
  - `apps/desktop/src/config-store.ts`
  - `apps/desktop/src/config-rpc.ts`
- session/runtime shape 以共享契约为准：
  - `packages/shared/src/session.ts`
  - `packages/shared/src/runtime.ts`

### 具体要做的事情

1. 打通主菜单按钮行为：
   - `继续`
   - `新游戏`
   - `加载存档`
   - `设置`
   - `退出`
2. 补齐新游戏初始化流程，使 provider/profile/model 选择可以真实创建 session
3. 启动时根据当前状态决定默认进入哪个 view
4. 配置缺失时给出明确 UI 反馈，而不是静默失败

### 完成标准

- 新安装/空状态下可以直接新建游戏并进入游戏界面
- 存在可继续状态时可以从菜单继续或加载

## 第三阶段：完成游戏内动作闭环

### 目标

让当前 galgame 壳真正可玩，完成 `互动 / 移动 / 调查` 与 `save/load/log` 的完整闭环。

### 重点文件

- `apps/desktop/src/renderer/views/GameView.vue`
- `apps/desktop/src/renderer/components/GameHud.vue`
- `apps/desktop/src/renderer/components/LogDrawer.vue`
- `apps/desktop/src/renderer/components/SaveLoadModal.vue`
- `apps/desktop/src/renderer/stores/session.ts`
- `apps/engine/src/services/session-service.ts`
- `apps/engine/src/routes/session.ts`

### 可能需要扩展的文件

如果当前分层不够清晰，再补动作弹层组件，例如：

- `InteractModal`
- `MoveModal`
- `InvestigateModal`

但要以现有结构为准，不为了“计划对齐”强行新建组件。

### 可复用基础

- `packages/shared/src/runtime.ts` 已经区分：
  - `timeline`
  - `log`
  - `scene`
  - `investigation_state`
- `apps/engine/src/services/session-service.ts` 已有动作推进能力
- `docs/research/2026-04-29-frontend-ui-handoff.md` 已确定游戏内视觉基线

### 具体要做的事情

1. 把 `互动 / 移动 / 调查` 从 UI 真实接到 engine action endpoint
2. 确保正式动作会正确更新：
   - timeline
   - scene
   - log
   - autosave
3. 确保 `调查` 只写入临时上下文，不进入正式 log
4. 确保 `调查` 在后续三次正式推进后正确过期
5. 补齐 HUD 里的：
   - `Q.save`
   - `Q.load`
   - `save`
   - `load`
   - `log`
   - `setting`
   - `hide`
6. 让 `LogDrawer` 和 `SaveLoadModal` 不再依赖占位数据，而是真实读取 session

### 完成标准

- 玩家可以在游戏壳里完成多轮推进
- 三类动作都可用
- save/load/log 可真实使用
- investigation 行为符合设计稿定义

## 第四阶段：加固存档与配置持久化

让 session、save、credential profile、settings 在桌面环境里稳定持久化。

### 重点文件

- `apps/desktop/src/config-store.ts`

- `apps/desktop/src/paths.ts`
- `apps/engine/src/services/session-service.ts`

- `packages/shared/src/session.ts`

### 可复用基础

- 当前磁盘路径布局已经在 `apps/desktop/src/paths.ts` 中定义
- 当前 save snapshot 行为已经有基础实现，并在 handoff 文档中说明

### 具体要做的事情

1. 验证并修正以下存档行为：
   - 自动存档
   - 快速存档
   - 普通手动存档

2. 确保 session/save 中只保存 profile 引用和模型快照，不保存 API Key 明文
3. 处理“存档引用的 credential profile 不存在或失效”的行为
4. 把设置页从占位入口补成 MVP 需要的真实配置页

### 完成标准

- 应用重启后可以恢复存档和配置
- 缺失 credential profile 时行为清晰，不破坏 session
- settings 改动可真实持久化

## 验证策略

### 自动化验证

在 repo root 执行：

```bash
npm test
npm run typecheck:test-contracts
npm run test:shared
npx vitest run apps/engine/src/server.test.ts
```

按需补充 focused test，尤其是：

- `apps/desktop/src/renderer/*.test.ts`
- `apps/desktop/src/renderer/stores/*.test.ts`
- `apps/desktop/src/config-*.test.ts`

### 桌面运行验证

```bash
cd apps/desktop
npx electrobun dev
```

重点验证：

1. 应用启动是否正常显示
2. 主菜单是否可操作
3. 新游戏能否进入正式游戏
4. `互动 / 移动 / 调查` 是否都能推进
5. `Q.save / Q.load / save / load / log` 是否可用
6. 重启应用后是否还能恢复状态

### UI 验证原则

- 保持 `docs/research/2026-04-29-frontend-ui-handoff.md` 中已确认的游戏内场景视觉基线
- 后续主要打磨对象是：
  - 主菜单
  - save/load
  - log
  - 动作弹层与系统层表现

## 开发顺序结论

接下来按以下顺序实际开工：

1. 先查清并修掉 Windows renderer 白屏
2. 再打通主菜单和新游戏
3. 再完成游戏内动作、save/load/log 闭环
4. 再加固持久化与设置
5. 再深化 `日记络络` 内容接入
6. 最后做 QA 和文档收尾

这份文档的作用不是替代详细 task list，而是作为“从现在到开发完成”的总路线图。后续每一轮实现，都应尽量落在这条顺序上，避免开发重心来回漂移。
